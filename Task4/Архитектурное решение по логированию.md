# Архитектурное решение по логированию

## Анализ

**Логирование необходимо для:**
- Shop API
- CRM API
- MES API
- Message Queue(RabbitMQ)

*Комментарий*: Действия и ошибки самого веб-интерфейса не логируем, т.к. на текущем этапе достаточно Яндекс.Метрик. Риски безопасности из-за публикации систем логирования в интернет выше, чем польза, которую можно получить на текущем этапе.

**Что логируем:**
- Жизненый цикл заказа
- Интеграционное взаимодействие между сервисами
- Действия пользователей

### Уровень INFO

| Система | Логирование |
| --- | --- |
|Shop API|Статус заказа: INITIATED <br/> Статус заказа: FILE_UPLOADED <br/> Статус заказа: SUBMITTED <br/> Факт сохранения данных в Shop DB <br/> Факт сохранения файлов в S3|
|MES API|Статус заказа: PRICE_CALCULATED <br/> Статус заказа: MANUFACTURING_STARTED <br/> Статус заказа: MANUFACTURING_COMPLETED <br/> Статус заказа: PACKAGING <br/> Статус заказа: SHIPPED <br/> Факт сохранения данных в MES DB <br/> Факт получения файла из S3 <br/> Факт отправки/получения сообщения из MessageQueue|
|CRM API|Статус заказа: MANUFACTURING_APPROVED <br/> Статус заказа: CLOSED <br/> Факт получения файла из S3 <br/> Факт отправки/получения сообщения из MessageQueue|
|Message Queue|disk space high watermark reached <br/> flow control activated|

Для статусов заказа логируем:
- Уникальный идентификатор заказа
- Предыдущий и новый статус
- Время события
- Инициатор события (логин/система)
- Система, в которой произошло изменение
- Результат выполнения

Для взаимодействия сервисов с Message Queue логируем:
- Тип операции (чтение/запись)
- Имя очереди
- Уникальный идентификатор заказа
- Тип события (например, "обновление статуса")
- Время события
- Система
- Результат выполнения

Для взаимодействия сервисов с S3 логируем:
- Тип операции (чтение/запись)
- Уникальный идентификатор заказа
- Данные о файле (путь, имя файла, размер)
- Время события
- Система
- Результат выполнения

Для взаимодействия сервисов с БД на запись логируем:
- Уникальный идентификатор заказа
- Тип операции (обновление/запись)
- Время события
- Система
- Результат выполнения

Для внутренних логов Message Queue логируем:
- Тип события
- Имя узла
- Время события

### Уровень DEBUG

Используется во время разработки нового функционала или решения инцидентов.
На продуктивном стенде возможно только временное включение.

## Мотивация

Компания показывает стабильный рост, но в тоже время растут и проблемы: несоблюдение сроков изготовления и доставки, медленная работа системы, жалобы и недовольство клиентов.
Благодаря логированию появится возможность сократить время реакции на инциденты, снизить число потерянных заказов и повысить доверие клиентов.

**Метрики, на которые повлияет логирование**
- NPS (Удовлетворенность клиентов) - повысится благодаря соблюдению сроков и обязательств
- COR (процент завершенных заказов) - повысится благодаря своевременной реакции на "потерянные" заказы
- MTTD (среднее время обнаружение инцидента в системе) - среднее время сократится до секунд(сейчас, предположительно, часы)
- MTTR (среднее время устранение инцидента) - сократится, благодаря повышению наблюдаемости

**Первый приоритет для логирования и трассировок**
1. MES API, т.к. является ядром системы для расчета и производства
2. Shop API, т.к. является основным сервисом по созданию заказов и взаимодействию с клиентом.
3. CRM API, т.к. влияет на обработку заказа и сроки его выполнения

## Предлагаемое решение

Внедрение централизованного логирования на базе ELK + Filebeat для Shop API, CRM API, MES API, Message Queue с использованием единого формата лога.

**Стек технологий:**
1. Filebeat
    Назначение: Сбор логов
2. Logstash
    Назначение: Парсинг, маскирование, сохранение логов в БД
3. Elasticsearch 
    Назначение: Хранение логов по индексам и соблюдение TTL
4. Kibana 
    Назначение: Интерфейс для анализа логов

**Процесс:**
1. Shop API, CRM API, MES API формирует логи в формате JSON и выводит их в stdout.
2. RabbitMQ формирует логи и сохраняет их в локальные файлы.
3. Filebeat собирает логи из stdout и файлов и отправляет в Logstash.
4. Logstash преобразует логи, маскирует данные(при необходимости) и отправляет их в ElasticSearch (в конкретные индексы)
5. ElasticSearch хранит логи в индексах
6. Kibana предоставляет интерфейс для анализа логов из ElasticSearch.

**Диаграмма контейнеров**
![Image Диаграмма контейнеров](https://github.com/Maksina/architecture-pro-alexandrite/blob/alexandrite/Task4/schemas/jewerly_c4_model.png)

**Индексы:**
- alexandrite-crm-prod-*: Индекс для CRM API. Срок хранения: 14 дней. Объем одного сообщения лога ~5Кб
- alexandrite-mes-prod-*: Индекс для MES API. Срок хранения: 14 дней. Объем одного сообщения лога ~5Кб
- alexandrite-shop-prod-*: Индекс для Shop API. Срок хранения: 14 дней. Объем одного сообщения лога ~5Кб
- infra-rabbitmq-*:  Индекс для RabbitMQ. Срок хранения: 14 дней. Объем одного сообщения лога ~10Кб

**Политики безопасности**
- Запрещено логировать чувствительную информацию(включая данные аутентификации и персональные данные) в открытом виде. В крайнем случае использовать маскирование.
- Пользовательский доступ к логам возможен только через Kibana с использованием механизмов аутентификации и авторизации
- Периодический аудит доступов к Kibana для выявления несанкционнированных доступов или подозрительных паттернов.

## Система сбора логов -> система анализа логов

1. Подключение Grafana к ElasticSearch и настройка дашбордов, алертов
2. ИИ-анализ логов на поиск аномалий
3. Автоматизация реакции на алерты и аномалии, например, при перегрузке API добавлять приложению реплики.
