### Архитектурное решение по трейсингу

## Мотивация

Компания показывает стабильный рост, но в тоже время растут и проблемы: несоблюдение сроков изготовления и доставки, медленная работа системы, жалобы и недовольство клиентов.
Благодаря трейсингу появится возможность сократить время реакции на инциденты, снизить число потерянных заказов и повысить доверие клиентов.

**Метрики, на которые повлияет трассировка**
- NPS (Удовлетворенность клиентов) - повысится благодаря соблюдению сроков и обязательств
- COR (процент завершенных заказов) - повысится благодаря своевременной реакции на "потерянные" заказы
- MTTD (среднее время обнаружение инцидента в системе) - среднее время сократится до секунд(сейчас, предположительно, часы)
- MTTR (среднее время устранение инцидента) - сократится, благодаря повышению наблюдаемости

## Предлагаемое решение

- Внедрение асинхронной отправка данных трейсинга в централизованную систему хранения и обработки.
- Настройка мониторинга и алертинга

*Что трассируем:* Взаимодействие между MES API и CRM API.
*Почему не трассируем Shop API -> Shop DB, Shop API -> S3, MES API -> S3, CRM API -> Shop DB:* Избыточно, т.к. логирования достаточно для того, чтобы отслеживать проблемы во взаимодействии с БД и хранилищами.

**Потребуется доработка:**
- MES API (Отправка трассировок, получение/передача traceId+spanId через RabbitMQ)
- CRM API (Отправка трассировок, получение/передача traceId+spanId через RabbitMQ) 

**Потребуется внедрение:**
- OpenTelemetry
- Jaeger
- Grafana

**Стек технологий:**
1. OpenTelemetry (SDK + Collector)
    Назначение:
        - SDK: Отправка трассировок из сервисов
        - Collector: Сбор данных и отправка в Jaeger
2. Jaeger
    Назначение: Хранение и визуализация деталей трассировки
3. Grafana
    Назначение: Визуализация метрик + настройка алертинга

**Состав трассировки**
| Поле | Описание|
| --- | --- |
|traceId|Глобальный идентификатор трассировки|
|spanId|Идентификатор операции|
|parentSpanId|Идентификатор родительской операции|
|timestamp|Время начала операции|
|serviceName|Название сервиса (MES API, CRM API)|
|duration|Продолжительность операции|
|orderId|Идентификатор заказа|
|status|Статус операции (успех/ошибка)|

## Компромиссы

1. Отсутствие трейсинга во взаимодействиях Shop API -> Shop DB, Shop API -> S3, MES API -> S3, CRM API -> Shop DB избыточно, т.к. логирования достаточно для того, чтобы отслеживать проблемы во взаимодействии с БД и хранилищами.
2. На текущий момент, все сервисы из стека позволяют использовать такой вид трейсинга, но если появится система, в которой это будет невозможно, то придется использовать дополнительный слой прокси.
3. Увеличение нагрузки на сервисы и сеть, т.к. каждое интеграционное взаимодействие будет пораждать дополнительный вызов на отправку трейса.
4. Увеличение стоимости инфраструктуры, т.к. потребуются дополнительные мощности и хранилища.

## Информационная безопасность

1. JaegerUi и Grafana не доступны из сети интернет. а так же выделенные в отдельные подсети.
2. Обязательная аутентифкация и авторизация, а также разделение по ролям доступа в JaegerUi и Grafana.
3. Маскирование или исключение из трассиовок любых чувствительных, персональных или аутентификационных данных.
